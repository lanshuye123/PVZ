## 命名规范

```
YYYY-MM-DD-NN-<slug>.md
```

| 段 | 含义 |
|---|---|
| `YYYY-MM-DD` | 该批改动**首个提交**的日期 |
| `NN` | 同日批次序号，从 `01` 开始 |
| `<slug>` | 英文短名，小写、连字符分隔 |

例：`2026-11-02-01-reanim-x64-fix.md`

文件名用英文是为了链接 URL 干净（中文名会被百分号转义）。
**文件内容一律用中文。**

## 新增一条变更

1. 复制下面模板生成新文件，按命名规范起名。
2. 在**上面的索引表**追加一行。
3. 如果这次改动影响了常青文档（`01`–`05`）里描述的行为，
   **同时更新那几篇**，并在记录里注明改了什么。

### 模板

```markdown
# 变更记录 · <标题>

| 项 | 值 |
|---|---|
| 日期 | YYYY-MM-DD |
| 提交 | `<hash>` |
| 类型 | 修复 / 新功能 / 重构 / 记录 |
| 影响 | 构建 / 渲染 / 存档 / 资源 / ... |
| 涉及文件 | `path/a.cpp`, `path/b.h` |

## 背景与症状

现象是什么，怎么复现。

## 根因

为什么会这样，**附上证据**（报错原文、实测数据、代码位置）。
区分"代码问题"和"环境问题"。

## 改动

改了什么，关键代码片段，为什么这么改。
如果放弃了别的方案，说明原因。

## 验证

怎么确认修好了 —— 最好是**可复现的命令或步骤**，而不是"我试过了"。

## 回退

`git revert <hash>`，或手工回退要点，以及回退后的后果。

## 相关

上游 issue、关联的常青文档、踩过的坑。
```

## 每份记录的最低要求

- ✅ **根因要有证据**，不要只写"改成 X 就好了"
- ✅ **验证要可复现** —— 给出命令或明确的观察点
- ✅ **必须写回退方式**
- ✅ 如果结论是"这不是代码问题"（环境/权限/工具链），**要明确写出来**，
  否则下一个人会继续在代码里找

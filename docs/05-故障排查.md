# 05 · 故障排查（Cookbook）

按**症状**或**报错关键词**查。所有修法都在本仓库的 Windows x64 + VS2022 环境实测过。

---

## 构建期

### 症状：`error C2001: 常量中有换行符` / `C1057: 宏扩展中遇到意外的文件结束` / `C3873` / `C3688`

**原因**：源文件编码与编译时指定的源码字符集不一致。
本工程历史上混用 UTF-8 / CP936 / CP1252，在没有指定源码字符集时会依赖
**编译机器的 ANSI 代码页**，于是英文系统能编、中文系统（CP936）编不过。

典型表现：

| 报错 | 位置示例 | 原因 |
|---|---|---|
| `C2001` + `C1057` | `LawnApp.cpp(1900)` | 无 BOM 的 UTF-8 里，中文全角问号 `？`(U+FF1F) 的字节 `EF BC 9F` 被按 CP936 解析，`9F` 与后面的 `"` 配成一个汉字，**吞掉了收尾引号** |
| `C3873` + `C3688` | `EditWidget.cpp(271)` | 字符字面量里是**裸 Latin-1 字节** `L'\xC0'` / `L'\xFF'` |

**修法**（本仓库已修，若你改动了源码后复现，按此检查）：

1. 确认 `SexyAppBase.vcxproj` 的 **8 个** `ClCompile` 配置都带 `/source-charset:utf-8`：

   ```powershell
   Select-String -Path SexyAppFramework\SexyAppBase.vcxproj -Pattern 'AdditionalOptions'
   # 8 条 ClCompile 应含 /source-charset:utf-8；2 条 Link 的 /INCREMENTAL 不含
   ```

2. 找出仍不是合法 UTF-8 的源文件并转成 **UTF-8 with BOM**：

   ```powershell
   $utf8 = New-Object System.Text.UTF8Encoding($false, $true)
   Get-ChildItem -Recurse -Include *.c,*.cpp,*.h,*.hpp,*.inc |
     Where-Object { $_.FullName -notmatch '\\\.git\\' } |
     Where-Object {
       try { [void]$utf8.GetString([IO.File]::ReadAllBytes($_.FullName)); $false }
       catch { $true }
     } | Select-Object -ExpandProperty FullName
   ```

3. 带 BOM 的文件 MSVC 会优先按 BOM 判断，不受系统代码页影响 —— 这是最稳的存法。

详见 [02-开发参考 §6](02-开发参考.md#6-源文件编码约定) 与 [06 §1](06-已实现改动.md#1-修复非-utf-8-系统区域下的编译失败)。

### 症状：`warning C4819: 该文件包含不能在当前代码页(936)中表示的字符`

**原因**：源码里含系统 ANSI 代码页表示不了的字符（通常是中文注释）。

加了 `/source-charset:utf-8` 之后这个警告会**完全消失**（实测 1158 → 0）。
如果还在刷，说明该文件没走到 uft-8 源码字符集，检查它是不是带 BOM 且被正确包含。

### 症状：`LINK : fatal error LNK1168: 无法打开 ...\PlantsVsZombies.exe 进行写入`

**原因**：**游戏正在运行**，Windows 锁住了 exe 文件。

**修法**：

```powershell
Get-Process PlantsVsZombies -ErrorAction SilentlyContinue   # 确认
Stop-Process -Name PlantsVsZombies -Force
```

然后重新构建。养成"构建前先关游戏"的习惯。

### 症状：克隆下来后 `bin\x64\` 里 DLL 缺失，或只有几十~几百字节

**原因**：**Git LFS 没有拉取**。小文件是 LFS 指针（文本），不是真正的 DLL。

**诊断**：

```powershell
git lfs ls-files
# 每行形如：<oid> * bin/x64/SDL3.dll
#   * = 已下载   - = 缺失/未下载
```

`bin\x64` 和 `bin\x86` 各应有 **12 个** DLL。任何一个显示 `-` 就是没拉全。

**修法**：

```powershell
git lfs fetch --all
git lfs checkout
```

拉完后**逐个校验大小**（这是最可靠的判断，不要只看文件存在）：

```powershell
foreach ($p in @('bin/x64/avcodec-62.dll','bin/x64/portaudio_x64.dll')) {
  $ptr  = git cat-file -p "HEAD:$p"
  $size = [int64](($ptr | Select-String '^size (\d+)$').Matches.Groups[1].Value)
  $real = (Get-Item $p).Length
  "{0,-32} expect={1,-10} actual={2,-10} {3}" -f $p,$size,$real,$(if($real -eq $size){'OK'}else{'BAD'})
}
```

**如果 `git lfs fetch` 卡住或报网络错误**，见下方
「[git 操作报 `sh: fatal error - couldn't create signal pipe`](#症状git-操作报-sh-fatal-error---couldnt-create-signal-pipe-win32-error-5)」。

### 症状：`fatal error: ImageLib.h: No such file or directory`

**原因**：用非 MSVC 工具链（如 MinGW / VS Code 的 `x86_64-w64-mingw32-gcc`）直接编译单个 `.cpp`。
本工程依赖 VS 项目的包含路径（`$(VC_IncludePath)` 等）和 vcxproj 里的
`include/ImageLib` 等目录，**不支持单文件 gcc 编译**。

**修法**：用 `PlantsVsZombies.sln` + MSBuild / Visual Studio 构建。

### 症状：几千条错误（8000+ errors）

**原因**：几乎都是**上游缺文件**导致的级联报错 —— 最常见是 LFS 没拉全、
游戏资源目录没放对、或 `assets/` 不完整。

**修法**：不要逐条看。先按顺序确认：
1. `git lfs pull` 完成且 24 个对象齐全；
2. 游戏目录名是 `Plants Vs Zombies` 或 `Plants Vs. Zombies`，里面有 `main.pak`；
3. 先只编一个文件或一个配置，取**最前面**的几条错误看 —— 后面的都是连锁反应。

## 运行期

### 症状：双击没反应 / 提示缺少某个 DLL

**原因**：`bin\` 下缺少运行时 DLL。

**诊断**：

```powershell
$dumpbin = "D:\Program Files\Microsoft Visual Studio\2022\Community\VC\Tools\MSVC\14.44.35207\bin\Hostx64\x64\dumpbin.exe"
& $dumpbin /dependents .\build\ReleaseGOTY_x64\bin\PlantsVsZombies.exe
```

**修法**：
- 缺 `SDL3.dll` / `avcodec-62.dll` 等 → LFS 没拉全（见上）
- 缺 `zlib1.dll` → `assets\` 不完整（它随仓库分发，不在 LFS 里）
- 干脆重建：删掉 `build\<cfg>_<plat>\bin\` 再构建一次，PostBuild 会补齐

### 症状：存档完全无法固化，每次启动都是全新的

> 这是最隐蔽的一类问题，本仓库专门排查过，过程见 [06 §4](06-已实现改动.md#4-一次存档排查的完整方法可复用)。

**先做一步分流**：启动一次游戏，看存档目录有没有被创建。

```powershell
Test-Path "$env:APPDATA\PopCap Games\PlantsVsZombies\userdata"        # user 模式
Test-Path ".\build\ReleaseGOTY_x64\bin\userdata"                      # portable 模式
Test-Path "$env:ProgramData\PopCap Games\PlantsVsZombies\userdata"    # legacy 模式
```

- **目录存在但每次还是全新** → 读路径问题，检查 `savedata.ini` 的 `mode` 是否指向了你以为的位置
- **目录根本没被创建** → **进程没有写权限**，往下看

#### 原因 A：可执行文件被打了「低完整性」标签（最常见且最难查）

Windows 有**强制完整性控制（MIC）**：一个**低完整性（Low）**进程**不能**写入
正常（Medium）完整性的位置 —— 包括 `%APPDATA%`、`%PROGRAMDATA%`、`%TEMP%`。
而 **Windows 会按可执行文件自身的完整性标签来决定进程的完整性级别**。

所以如果 exe 被打了 Low 标签，游戏就是 Low 进程 → 建不出 `userdata\` 目录 →
`fopen(..., "w+b")` 报 `ENOENT` → **每次启动都是全新档**。

**诊断一：看 exe 的标签**

```powershell
icacls .\build\ReleaseGOTY_x64\bin\PlantsVsZombies.exe | Select-String 'Mandatory Label'
# 正常：没有输出（默认 Medium）
# 有问题：Mandatory Label\Low Mandatory Level:(I)(NW)
```

**诊断二：看运行中进程的真实完整性级别**

```powershell
Add-Type -TypeDefinition @'
using System; using System.Runtime.InteropServices;
public class Tok {
  [DllImport("kernel32.dll")] public static extern IntPtr OpenProcess(uint a, bool i, int pid);
  [DllImport("kernel32.dll")] public static extern bool CloseHandle(IntPtr h);
  [DllImport("advapi32.dll")] public static extern bool OpenProcessToken(IntPtr p, uint d, out IntPtr t);
  [DllImport("advapi32.dll")] public static extern bool GetTokenInformation(IntPtr t, int c, IntPtr i, uint l, out uint r);
  public static int Integrity(int pid) {
    IntPtr ph = OpenProcess(0x1000, false, pid); if (ph == IntPtr.Zero) return -1;
    IntPtr tok; if (!OpenProcessToken(ph, 0x0008, out tok)) { CloseHandle(ph); return -2; }
    IntPtr buf = Marshal.AllocHGlobal(128); uint rl; int rid = -3;
    if (GetTokenInformation(tok, 25, buf, 128, out rl)) {
      IntPtr sid = Marshal.ReadIntPtr(buf); byte cnt = Marshal.ReadByte(sid, 1);
      rid = Marshal.ReadInt32(sid, 8 + 4*(cnt-1));
    }
    Marshal.FreeHGlobal(buf); CloseHandle(tok); CloseHandle(ph); return rid;
  }
}
'@
$p = Start-Process .\build\ReleaseGOTY_x64\bin\PlantsVsZombies.exe -PassThru
Start-Sleep 5
"RID = $([Tok]::Integrity($p.Id))   # 4096=Low 8192=Medium 12288=High"
Stop-Process -Id $p.Id -Force
```

`RID = 4096` 即确诊。

**修法**：把标签提升回 Medium。

```powershell
icacls .\build\ReleaseGOTY_x64\bin\PlantsVsZombies.exe /setintegritylevel Medium
```

**为什么会出现 Low 标签？** 工作目录本身带 Low 标签时，在里面创建的文件会**继承**它。
常见来源：从**沙箱化 / 受限的构建环境**里编译或复制文件。

> **根治办法**：**在普通（非沙箱）环境里用 VS2022 构建**，产物天生是 Medium。
> 只要构建环境把工作目录标成了 Low，每次重新编译都会再次污染 exe，
> 必须重新执行一次上面的 `icacls`。

**注意区分**：Low 标签只影响**写**。游戏读自己目录里的资源完全正常，
所以现象会精确地表现为"游戏能玩，但存档留不住"。

#### 原因 B：存档目录权限真的不对

确认当前用户对目标目录有写权限：

```powershell
$d = "$env:APPDATA\PopCap Games\PlantsVsZombies"
(Get-Acl $d).Access | Format-Table IdentityReference, FileSystemRights, AccessControlType
# 你的账户应有 FullControl
```

`%PROGRAMDATA%` 是**全机器共享**目录，某些受限账户不可写 —— 这也是默认模式
从 `legacy` 改成 `user`（`%APPDATA%`）的原因之一。改用
`savedata.ini` 的 `mode = portable` / `static` 指到你可写的位置即可。

#### 原因 C：配置指向了别处

```powershell
Get-Content .\build\ReleaseGOTY_x64\bin\savedata.ini | Select-String '^mode'
```

注意你改的是不是**正在运行的那个 exe 旁边**的配置。详见 [04-存档配置](04-存档配置.md)。

### 症状：画面不是 800×600 / 能看到"可见区之外"的区域

**原因**：上游在 `LawnApp::Init()` 里硬编码了 `#define _WIDE_SCREEN`，
把画布从 800×600 撑到 **1066×600** 并整体偏移 133px，
而美术资源只覆盖 800×600，多出来的 266px 就露出了本不该出现的区域。

**修法**：本仓库已修复（注释掉那个 `#define`）。若你的分支还有这个问题：

```cpp
// LawnApp.cpp 约 368 行
//#define _WIDE_SCREEN        // ← 加上注释
```

详情与上游 issue 见 [06 §2](06-已实现改动.md#2-恢复原始-800600-渲染)。

### 症状：画面比原版模糊 / 像素边缘发虚

**原因**：工程没有设置默认纹理缩放模式，SDL3 默认是**双线性（LINEAR）**。
窗口被放大或全屏时整幅画面被平滑放大。

**修法**：在 `SDL_CreateRenderer` 之后加：

```cpp
SDL_SetDefaultTextureScaleMode(mSDLRenderer, SDL_SCALEMODE_NEAREST);
```

详见 [02-开发参考 §2](02-开发参考.md#缩放过滤)。

### 症状：缺少 reanim / particle 文件报错

**原因**：x64 构建要求每个新加的 reanim **同时**存在两份：

- `reanim\xxx.reanim`（源）
- `compiled\reanim\xxx.reanim.compiled`（编译产物）

particle 与 trail 同理，放在 `particles\` 和 `compiled\particles\`。
**Win32 和 x64 都适用。**

**修法**：补齐缺失的那一份。参见上游 issue
[#58](https://github.com/InLiothixi/stabledecompile/issues/58)。

### 症状：打地鼠（Whack-A-Zombie）关卡疯狂报 `DataArrayGet` 错误

这是上游已知未修问题（issue
[#57](https://github.com/InLiothixi/stabledecompile/issues/57)），
与灌木丛的资源组织有关。目前只能绕开该关卡。

### 症状：2009 版崩溃，提示 `IMAGE_REANIM_ZOMBIE_PAPER_PAPER1` 未定义

上游已知问题（issue
[#56](https://github.com/InLiothixi/stabledecompile/issues/56)）。
该资源在 2009/GOTY 里可能不存在。临时办法是从 `Zombie.cpp` 里去引用。

## 工具 / 环境

### 症状：git 操作报 `sh: fatal error - couldn't create signal pipe, Win32 error 5`

完整形态：

```
      0 [main] sh (20304) C:\Program Files\Git\usr\bin\sh.exe: *** fatal error - couldn't create signal pipe, Win32 error 5
...
fatal: the remote end hung up unexpectedly
```

**原因**：git 通过 MSYS 的 `sh.exe` 执行 **LFS 过滤器**，而受限/沙箱环境
不允许它创建信号管道。**与仓库本身无关**，不要因此去 `git reset --hard`。

受影响的操作：任何会触发 LFS 过滤器读写工作区的命令 —— `git status`、`git reset`、
`git checkout`、`git lfs pull`。不受影响的：`git ls-files`、`git cat-file`、
`git read-tree`、`git log`。

**修法**：

- 在**普通（非沙箱）终端**里执行 git 操作；
- 临时绕过（只读场景）：

  ```powershell
  git -c filter.lfs.process= -c filter.lfs.required=false status
  ```

- 如果 `.git/index` 已被破坏到 `git ls-files` 返回 0（所有文件显示为 staged deletion），
  可以用下面这条**只改索引、不动工作区**的命令重建：

  ```powershell
  git -c filter.lfs.smudge= -c filter.lfs.process= -c filter.lfs.required=false read-tree HEAD
  ```

  > 千万不要用 `git reset --hard` 或 `git checkout .` 来处理这种状态 —— 会覆盖工作区。

### 症状：git 推送/拉取时反复告警 `TLS certificate verification has been disabled!`

**原因**：git 全局配置里关掉了证书校验：

```powershell
git config --global --get http.sslVerify      # false 就是问题所在
```

**风险**：这会影响**所有** HTTPS 仓库，中间人可以替换你拉到的代码而不被发现。

**修法**（恢复安全默认值）：

```powershell
git config --global --unset http.sslVerify
```

如果只有某个环境/域名确实因为证书问题连不上，正确做法是**只对该域名放行**：

```powershell
git config --global http."https://<host>/".sslVerify false
```

### 症状：全盘搜索某个文件很慢 / 结果不全

用 `dir /s /b`（cmd 内建，比 `Get-ChildItem -Recurse` 快很多），并在后台跑：

```powershell
cmd /c "dir C:\avcodec-62.dll /s /b 2>nul"
```

注意 `dir` 没找到文件时返回退出码 1，这**不代表命令失败**。

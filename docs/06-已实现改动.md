## 1. 修复非 UTF-8 系统区域下的编译失败

### 根因

工程历史上混用三种源码编码，且**没有指定源码字符集**，导致编译结果依赖
编译机器的 ANSI 代码页。实测扫描 1066 个源文件：

| 编码 | 数量 | 说明 |
|---|---|---|
| 纯 ASCII | 990 | 无关紧要 |
| UTF-8（无 BOM） | 63 | 在 CP936 下被按 GBK 解析 |
| UTF-8 with BOM | 6 | MSVC 能正确识别 |
| **其他编码** | **7** | 4 个 CP936 + 3 个 CP1252 |

在中文系统（**CP936**）上产生两类**硬错误**：

**① `LawnApp.cpp:1900` —— 收尾引号被吞**

```cpp
_S("买下这个物品？")
```

`？` 是 U+FF1F，UTF-8 字节为 `EF BC 9F`。按 CP936 解析时：

- `EF BC` 被当成一个双字节汉字
- 剩下的 `9F` 是 CP936 的**首字节**，于是和后面的 `"`(0x22) 配成第二个汉字

结果**字符串字面量的收尾引号被吃掉**，编译器一路读到行尾：

```
error C2001: 常量中有换行符
error C1057: 宏扩展中遇到意外的文件结束
```

**② `EditWidget.cpp:271` —— 裸 Latin-1 字节字面量**

```cpp
(((unsigned int)theChar >= (unsigned int)(L'\xC0')) &&
 ((unsigned int)theChar <= (unsigned int)(L'\xFF')))
```

源码里是**真实字节** `4C 27 C0 27` 和 `4C 27 FF 27`，即 Latin-1 的 `À` / `ÿ`
（程序作者本意就是用 0xC0–0xFF 做 Latin-1 范围判断）。在 CP936 下这两个字节
被当作 DBCS 首字节：

```
error C3873: "0xf8f5": 不允许将此字符作为标识符的第一个字符
error C3688: 文本后缀""无效
error C2001 / C2015 / C2059 / C2143 ...
```

**③ 1158 条 `C4819`**（文件含当前代码页无法表示的字符），几乎每个文件都刷。

### 改动

**a. 所有配置加 `/source-charset:utf-8`**

`SexyAppFramework/SexyAppBase.vcxproj` 的 **8 个** `ClCompile` 配置：

```xml
<AdditionalOptions>/source-charset:utf-8 /wd4996 %(AdditionalOptions)</AdditionalOptions>
```

（只加在 `ClCompile` 上；2 处 `Link` 的 `/INCREMENTAL` **未动**。）

**b. 7 个非 UTF-8 文件转成 UTF-8 with BOM**

按各自**真实编码**转换，不是一刀切：

| 文件 | 原编码 | 判据 |
|---|---|---|
| `Lawn/Cutscene.h` | CP936 | `A1 BE CD C6 CF FA B4 F7 B7 F2 B5 BD BC C6 CA B1 A1 BF` → 「推销戴夫倒计时」 |
| `Lawn/System/DataSync.h` | CP936 | `CE B4 D5 D2 B5 BD` → 「未找到」 |
| `Lawn/Widget/ContinueDialog.cpp` | CP936 | `A1 A2` → 「、」 |
| `Lawn/Widget/NewOptionsDialog.cpp` | CP936 | `A1 A2` → 「、」 |
| `SexyAppFramework/EditWidget.cpp` | CP1252 | `C0` / `FF` → `À` / `ÿ` |
| `include/dx8sdk/edevdefs.h` | CP1252 | `92` → `’`（device's） |
| `include/dx8sdk/xprtdefs.h` | CP1252 | `92` → `’` |

为什么用 **BOM**：带 BOM 时 MSVC **优先按 BOM** 判断编码，与系统代码页无关，
即使以后有人去掉 `/source-charset:utf-8` 也不会退化。

为什么 `/source-charset:utf-8` **只改源码字符集**、不动执行字符集：
narrow 字面量仍按系统 ANSI（CP936）落地，保持与原版一致的行为。
实测 `C4566`（字面量字符丢失）为 **0**，说明没有任何字符丢失。

**c. `.gitignore` 增加 `/_encoding_backup/`**

排查期间保留了 7 个原文件的备份（敏感：这是唯一保存原始字节的地方）。
放在仓库根但**不入库**。

### 验证

```powershell
$msbuild = "D:\Program Files\Microsoft Visual Studio\2022\Community\MSBuild\Current\Bin\MSBuild.exe"
& $msbuild PlantsVsZombies.sln /p:Configuration=ReleaseGOTY /p:Platform=x64 /m `
    "/flp:logfile=build.log;verbosity=normal"
```

期望：`0 个错误`；日志里 `C4819` 计数为 **0**（此前 1158）。

### 回退

```powershell
git revert e2636d3
```

或手工：把 `_encoding_backup\` 下的 7 个文件复制回原位，并移除 8 处
`/source-charset:utf-8`。**回退后中文系统将无法编译。**

## 2. 恢复原始 800×600 渲染

### 根因

`LawnApp::Init()` 里有一行**无条件**的宏定义（无 `#ifndef` 保护）：

```cpp
#define _WIDE_SCREEN
#ifdef _ULTRA_WIDESCREEN
    mWidth = 1280;  mHeight = 720;
    mDDInterface->mWideScreenOffsetX = 240;
    mDDInterface->mWideScreenOffsetY = 60;
#elif defined(_WIDE_SCREEN)
    mWidth = 1066;  mHeight = 600;
    mDDInterface->mWideScreenOffsetX = 133;
#endif
gBoardBounds = Rect{ 0, 0, mWidth, mHeight };
```

原版是 **800×600**（`BOARD_WIDTH` / `BOARD_HEIGHT`，`GameConstants.h`），
构造函数本来也正确设成 800×600，但这里被强制改成 **1066×600**：

- `1066 − 800 = 266`，`266 / 2 = 133` —— 正是那个硬编码的偏移量
- 画面左右各被撑出 133px，而**美术资源只覆盖 800×600**
  → 于是能看到"可见区之外"的区域

**更关键的是它把框架自带的宽屏系统架空了**：

| 位置 | 内容 |
|---|---|
| `SexyAppBase.cpp` | `mWidths[] = { 800, 1066, 1280 }`、`mWidescreenAware = true`、`mResolutionMode = 0`（→ 800×600） |
| `DDInterface.cpp` | `mWideScreenExtraWidth = mWidth - gSexyAppBase->mWidth; mWideScreenOffsetX = extra / 2` |

框架的设计是：`gSexyAppBase->mWidth` 保持 800×600 作为**设计基准**，
由 `mResolutionMode` 选择实际分辨率。而 LawnApp 在 DDInterface 之前就把
`mWidth` 改成 1066，于是 DDInterface 算出 `1066 − 1066 = 0` —— **通用机制失效**，
只有那个硬编码的 133 生效。

旁证这个功能没做完：

- `GameConstants.h` 里 `WIDE_BOARD_WIDTH = 800`，与 `BOARD_WIDTH` **完全相同**
- `_WIDE_SCREEN` 分支只设了 `offsetX`，**漏设 `offsetY`**（对比 `_ULTRA_WIDESCREEN` 两个都设）

上游 issue：[#55 Game resolution is broken](https://github.com/InLiothixi/stabledecompile/issues/55)（未关闭）

### 改动

`LawnApp.cpp`：把那一行 `#define` 注释掉，并写清原因与 issue 链接。
两个分支都由 `#ifdef` / `#elif` 保护，且这两个宏全库**再无任何 `#define`**，
所以两个分支都成为死代码 → `mWidth/mHeight` 回落到构造函数的 800×600。

### 验证

```powershell
# 宏不再被定义
Select-String -Path LawnApp.cpp -Pattern '^\s*#\s*define\s+(_WIDE_SCREEN|_ULTRA_WIDESCREEN)'
# 应无输出（只有 #ifdef / #elif 引用）
```

运行后窗口应为 **800×600（4:3）**，左右不再有多余区域。

### 回退

```powershell
git revert 3b8caf7
```

想**正确**启用宽屏，应改走框架的 `mResolutionMode`（配合 `mWidths[]`），
而不是恢复这个硬编码。

## 3. 可配置的存档位置

用户手册在 [04-存档配置](04-存档配置.md)。这里讲实现。

### 设计

| 决策 | 取值 | 理由 |
|---|---|---|
| 配置文件名 | `savedata.ini` | 自描述，且与"调试/控制静态配置文件"的定位一致 |
| 位置 | **exe 旁边** | 随程序分发；`instance` / `portable` 模式本身就依赖这个位置 |
| 分发方式 | 放进 `assets/` | PostBuildEvent 会 `robocopy assets → bin`，无需改构建脚本 |
| 格式 | 极简 INI | 人类可读可改，无需引入 XML/JSON 依赖 |
| 默认模式 | `user`（`%APPDATA%`） | 现代惯例（对标 `%APPDATA%\.minecraft`），且天然避开 ProgramData 的权限/完整性问题 |
| 兜底 | 未知/缺失 → `user` | 删掉配置文件也不能让游戏挂掉 |
| `path` 语义 | **根目录**，游戏在其下建 `userdata\` | 与其它四种模式保持一致，行为可预测 |

### 实现

**a. `SexyAppFramework/Common.h` / `Common.cpp`** — 新增：

```cpp
typedef std::map<SexyString, SexyString> IniValueMap;

bool       LoadIniFile(const SexyString& theFileName, IniValueMap* theValues);
SexyString GetExeDirectory();                    // exe 所在目录，无尾斜杠
void       SetLaunchDirectory(const SexyString& theDir);
SexyString GetLaunchDirectory();                 // 启动时的工作目录
SexyString ResolveSaveDataFolder(const SexyString& theCompanyName,
                                 const SexyString& theProductName,
                                 const SexyString& theCommonAppData,
                                 const SexyString& theRoamingAppData);
```

解析要点：

- 支持 UTF-8 BOM；`#` / `;` 注释；忽略 `[section]`
- 键名 `StringToLower`，**大小写不敏感**
- **注释只在其前是空白时才算注释**，因此路径里可含 `#` / `;`

模式分派（简化）：

```cpp
if      (mode == "portable") aFolder = GetExeDirectory();
else if (mode == "instance") aFolder = GetLaunchDirectory();
else if (mode == "static" && !path.empty())
    aFolder = isAbsolute(path) ? path : GetExeDirectory() + "\\" + path;
else if (mode == "legacy")   { base = commonAppData; needsSuffix = true; }
else                         { base = roamingAppData; needsSuffix = true; }   // user + 兜底
```

`needsSuffix` 表示还要拼上 `<Company>\<Product>`；`base` 为空（例如
`SHGetFolderPath` 失败）时退回 exe 目录，避免拼出 `\PopCap Games\...` 这种根路径。

**b. `SexyAppFramework/SexyAppBase.cpp`** — 用解析结果替换原先写死的路径：

```cpp
SexyString aDataPath = ResolveSaveDataFolder(mFullCompanyName, mProdName,
                                             aCommonAppData, aRoamingAppData);
SetAppDataFolder(aDataPath);
MkDir(aDataPath);                        // 启动即创建根目录
MkDir(aDataPath + _S("userdata"));       // 以及 userdata，便于确认落点
```

**顺带修掉同一段代码里的两个隐患**：

1. `SexyChar aPath[MAX_PATH];` **未初始化**就读 —— 若 `SHGetFolderPath` 失败，
   会拿栈上的垃圾去拼路径。已改为 `= { 0 }`。
2. `SHGetFolderPathFunc aFunc` 在 `if` 内部**被重复声明**，导致外层那个始终为
   `NULL`，`shfolder.dll` 的回退分支实际上从未生效。已改为赋值。

另外把原来被注释掉的 `//MkDir(aDataPath);` 正式启用（改为无条件创建）。

**c. `main.cpp`** — 在**改变工作目录之前**捕获启动目录：

```cpp
{
    char aLaunchDir[MAX_PATH] = { 0 };
    if (GetCurrentDirectoryA(MAX_PATH, aLaunchDir) != 0)
        Sexy::SetLaunchDirectory(aLaunchDir);
}
```

顺序很关键：`SexyAppBase::Init()` 后面会 `sexychdir(mChangeDirTo)`，
在那之后再取 `GetCurrentDirectory` 就拿到的是被改过的目录了。

同时把 `main.cpp` 里那份同名的文件级 `GetExeDirectory()` 删掉，
统一用 `Sexy::GetExeDirectory()`（否则 `using namespace Sexy;` 会造成重载歧义，
实测报 `error C2668`）。

**d. `assets/savedata.ini`** — 默认配置，带完整注释的模板，随构建复制到 exe 旁边。

### 验证（7/7 实测通过）

每个用例都是：清理候选目录 → 写配置 → **实际运行游戏** → 检查哪个目录出现了
`userdata\`（因为启动时会主动创建，所以目录出现即可证明模式生效）。

| 用例 | `savedata.ini` | 期望目录 | 结果 |
|---|---|---|---|
| `user` | `mode = user` | `%APPDATA%\...\userdata` | ✅ PASS |
| `portable` | `mode = portable` | `<bin>\userdata` | ✅ PASS |
| `instance` | `mode = instance`（以 `C:\...\pvzinst` 为工作目录启动） | `C:\...\pvzinst\userdata` | ✅ PASS |
| `static` | `mode = static` + `path = C:\...\pvzstatic` | `C:\...\pvzstatic\userdata` | ✅ PASS |
| `legacy` | `mode = legacy` | `%PROGRAMDATA%\...\userdata` | ✅ PASS |
| 未知模式 | `mode = nonsense` | 回退到 user | ✅ PASS |
| 无配置文件 | （删除文件） | 回退到 user | ✅ PASS |

### 回退

```powershell

```

回退后恢复成固定的 `%PROGRAMDATA%\PopCap Games\PlantsVsZombies\`，
且该目录**不再**在启动时创建。

## 4. 一次存档排查的完整方法（可复用）

"存档不保存"是最难从代码上判断的一类问题 —— 静态阅读时路径、逻辑、权限
**看起来全部正确**。这次排查最后是靠**注入探针拿到运行时真相**解决的，
方法值得复用。

### 为什么不能只读代码

静态检查过的、结论是"没问题"的部分：

- `gAppDataFolder` 解析逻辑正确
- 读写路径一致（`userdata/users.dat` 与 `userdata/user%d.dat`）
- `p_fopen` **确实**会回退到真实文件系统（`PakInterface.cpp:212`），pak 不会挡读取
- 存档目录 ACL 正常（用沙箱 ACL 诊断脚本判定为 `NOT_THIS_CLASS`，调用者拥有 `FullControl`）
- 游戏代码里**没有**任何降低自身完整性的调用

**以上全部正确，但存档依然不保存。** 静态分析的盲区在于**运行时的进程上下文**。

### 有效手法：分层探针

在关键路径上插临时日志（写到固定文件），逐层排除：

| 层 | 探针内容 | 得到的结论 |
|---|---|---|
| 1 | `ResolveSaveDataFolder` 的返回值 | 路径解析**正确**：`C:\ProgramData\PopCap Games\PlantsVsZombies\` |
| 2 | `ProfileMgr::Load` 的完整路径 + 读取结果 | 读路径**正确**，只是文件不存在 |
| 3 | `ProfileMgr::Save` 是否被调用 | 未被调用（无 GUI 输入时不触发，符合预期） |
| 4 | 直接调 `CreateDirectoryA` 试写 | **失败**！`lasterr=5`（ACCESS_DENIED） |
| 5 | `MkDir` 内部逐步 `_mkdir` + `errno` | 父目录 `errno=17`(EEXIST) 正常，最后一级 `errno=13`(EACCES) |
| 6 | 用 `GetTokenInformation(TokenIntegrityLevel)` 读自身完整性 | **`RID=4096`（Low）** ← 决定性证据 |

第 6 层是关键。有了它，前面所有矛盾都解释通了。

### 收获：两个容易踩的坑

**坑一：`errno` 与 Win32 错误码要一起看**

`_mkdir` 返回的 `errno=13` (EACCES) 只是 Win32 错误 5 (ACCESS_DENIED) 的映射。
直接用 `CreateDirectoryA` + `GetLastError()` 拿到的信息更准：

```cpp
SetLastError(0);
BOOL r = CreateDirectoryA(dir, NULL);
DWORD e = GetLastError();   // 5=拒绝访问 3=路径不存在 183=已存在
```

**坑二：`%TEMP%` 和 `%APPDATA%` 也会被拒绝**

我们一开始以为只有 `%PROGRAMDATA%` 出问题。实测 Low 进程对
`C:\ProgramData\...`、`C:\Users\...\AppData\Local\Temp\...` 都是 `lasterr=5`，
**只有工作区（同样带 Low 标签）能写**。这个"能写 A 不能写 B"的模式本身就是
强制完整性控制（MIC）"禁止向上写"的典型特征 —— 见到这个模式就该去查完整性级别。

### 最终结论

可执行文件继承了构建环境的 **Low 完整性标签** →
Windows 按该标签把进程启动为 Low 完整性 →
Low 进程不能写入 Medium 完整性的 `%PROGRAMDATA%` / `%APPDATA%` / `%TEMP%` →
`MkDir` 建不出 `userdata\`，`fopen` 报 ENOENT →
**每次启动读不到档案，表现为全新档**。

对症处理见 [05-故障排查](05-故障排查.md#症状存档完全无法固化每次启动都是全新的)。

> **副产品**：这次排查也说明"在新位置创建目录"这件事本身有诊断价值。
> 因此第 3 项改动特意让游戏**启动时就创建**所选根目录和 `userdata\` ——
> 以后遇到类似问题，看一眼目录在不在就能分流，不必再插探针。
